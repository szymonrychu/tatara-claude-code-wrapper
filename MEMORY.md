- 2026-08-22 (claude-usage-gate-feed, semver:minor) **A new silent `cmd/cc-statusline` binary, installed via `settings.json`'s `statusLine` key, is now the live data feed for tatara-operator's Claude subscription usage gate - previously deployed but evaluating nothing.** Claude Code's statusline command receives a JSON payload on stdin carrying `rate_limits.{five_hour,seven_day}.{used_percentage,resets_at}`; `cc-statusline` forwards it to the wrapper's existing unauthenticated loopback internal router (`POST /internal/account-usage`, trust boundary is the pod's own network namespace, same as `/internal/turn-complete`), which stores it in a newest-wins `internal/ratelimit.Latest` holder; `finalizeTurn` reads the holder at delivery time and rides it out on the turn-complete callback to the operator as `accountUsage` (`cmd/wrapper/callback_payload.go`). **`resets_at` is UNIX EPOCH SECONDS (a JSON number), NOT RFC3339, and this deliberately differs from `/api/oauth/usage`, whose `usageWindow.ResetsAt` genuinely IS RFC3339** (`internal/accountusage/client.go` on the operator side) - the two Claude-usage sources disagree with each other, verified by extracting v2.1.226's own embedded statusline schema doc from the bundled binary (full write-up: session scratchpad `spike-verdict.md`, transcribed into the plan's SPIKE VERDICT). `cc-statusline`'s `window.ResetsAt` is decoded as a plain `int64`; an RFC3339 string there fails the decode and the report is DROPPED rather than coerced, because coercing would yield a zero reset the gate would misread as a live window. **`rate_limits` is absent until the session's first API response, and `five_hour`/`seven_day` are each individually optional even then** (confirmed empirically: spike runs with `cost.total_api_duration_ms == 0` produced `rate_limits: null` while every other documented field was present) - so the binary posts NOTHING rather than a zero-valued snapshot, and `callbackPayload.AccountUsage` is a nil-omitempty pointer end to end (`app.accountUsage()` returns nil whenever the holder has nothing), because a 0% with a 0 reset would read to the operator's admission gate as "0% used", exactly the silent-inert failure this whole feature exists to fix. **The statusline does NOT fire in `-p`/print mode** (verified: a print-mode run with a configured statusline made a real API call and never invoked the command) - the wrapper is safe only because it runs one persistent INTERACTIVE `claude` over a PTY and never `-p`, which was already documented as load-bearing for the PTY path and is now ALSO load-bearing for this feed: moving to print mode would silently kill the usage feed and the operator's gate would quietly go back to admitting everything. The feed is subscriber-only by construction: agent pods authenticate with `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token`, which qualifies; a pod on `ANTHROPIC_API_KEY` would never report. Workspace trust does NOT suppress it - confirmed empirically against a scratch `HOME` seeded with exactly the three keys `internal/bootstrap/claudejson.go`'s `hasTrustDialogAccepted` write already produces, and a workspace absent from `projects` DID show the trust dialog, confirming the mechanism is real and that the existing bootstrap satisfies it with no new code. `cc-statusline` diverges from `cc-stop-hook` in exactly one way, deliberately: one attempt, 500ms timeout, no retries - the Stop hook's payload is irreplaceable so it retries 5x over 25s, but the statusline fires on every TUI redraw and its payload is superseded seconds later, so retrying would only add latency to a redraw a human never sees in an agent pod. The snapshot deliberately bypasses `turn.Record` entirely (never threaded through `session.HookResult`/`turn.Record` the way `TurnTokens` is) because it is account-wide truth - one subscription shared by the whole fleet - not a per-turn accounting value; it is read straight from the holder in `finalizeTurn`, which is the only place it is actually needed. `STATUSLINE_PATH` gets no chart value and no CLI flag, deliberately mirroring `HOOK_PATH`, which also relies on its Go-side baked default (`/usr/local/bin/cc-statusline`) rather than chart-level drift. **Honest residual: a POPULATED `rate_limits` block was never witnessed locally.** Every scripted attempt to drive a turn through a PTY session failed to submit (`cost.total_api_duration_ms` stayed 0), and print mode does not fire the statusline at all, so there was no local path that both makes an API call and renders a status line. The schema and semantics are settled from Claude Code's own embedded documentation, and a live `rate_limit_event` from a real print-mode call independently corroborated the unix-seconds encoding and that subscription rate-limit state exists for this account - but population in an actual agent pod is high-confidence, not observed. `ccw_statusline_reports_total{result="ok"}` staying 0 in a live pod is the signal that this specific assumption is what broke, not anything in the wrapper's own code.

- 2026-08-10 (resumed-workspace-safety, semver:minor): the resumed-workspace git safety contract, a HARD PREREQUISITE for mounting a per-Task PVC at `/workspace`. Against the old bootstrap a volume was strictly WORSE than none: `checkoutTaskBranch` ran `git checkout -b <taskBranch>` when the branch existed locally but not on origin (fatal - and with a volume that fatality is permanent, so the pod crash-loops to the 24h residency cap since `maxPodRecreations` was deleted), and `checkout -B <b> FETCH_HEAD` when both existed, hard-resetting away exactly the unpushed commits the volume exists to preserve. New `internal/bootstrap/resume.go` runs `PrepareWorkspace` before the `.git` stat that skips the clone: Phase A wipes a `.git` git itself will not open (killed mid-clone), B clears stale locks unconditionally (no live git process on a fresh pod, and an mtime heuristic is a trap because the PVC's clock outlived the pod), C aborts any half-applied merge/rebase/cherry-pick/revert/bisect, D COMMITS uncommitted tracked work rather than stashing it (a stash is invisible to the agent and to the turn finaliser's `git add -A`, so stashing is a slower way of losing it) with `unstageOversizedBlobs` first, and leaves untracked output alone. Phase E replaces the fatal pair with four arms on (localExists, remoteExists): yes/no is plain checkout plus a push, yes/yes is merge-or-abort and NEVER `-B`. The one rule everything serves: local commits are authoritative, the remote is authoritative for nothing, every operation is additive - force-push is denied by the settings deny list, so a branch this code reset could never be published again. Three design points worth keeping: `persistent` is passed into `checkoutTaskBranch` rather than inferred, so a fresh clone keeps PR #159's exact behaviour (a just-cloned repo has no `refs/heads/<taskBranch>` to find anyway) and its tests stay honest; the rescue commit's sha is read out of `.git/HEAD` because `GitRunner` returns only an exit code and widening it would touch every test double; and a rescue commit made on a detached HEAD also gets branch `tatara-bootstrap-rescue`, or Phase E's checkout would leave it reachable only through the reflog. Phase F's `.tatara-workspace.json` wipes the workspace on a taskName mismatch (a per-Task PVC cannot legitimately hold another Task's tree, and guessing is worse than re-cloning) but keeps a changed repo set, leaving removed checkouts on disk because they may hold uncommitted work. Surfacing follows the measured shape of the data - over 7 days `bootstrap_reconcile` was conflict 67 / up_to_date 4 / merged 2, so conflict is the HOT path: PR #159's directive gained a third, middle tier ("workspace recovered from an interrupted session") and renders the local-vs-remote merge BEFORE the base merge, because merging the base into a branch still missing half its own commits reconciles nothing. REVIEW CORRECTED THE ONE DESTRUCTIVE PATH, and it is the entry worth remembering: the first cut escalated a FAILED abort over a dirty tree to wipe-and-re-clone, which destroys uncommitted work in the exact situation where the previous session's state is LEAST understood - a failed abort is the strongest reason not to delete, not a licence to. `rescueUnabortable` now claims a dedicated rescue branch (`tatara-bootstrap-rescue-aborted`, numeric suffixes so a second interrupted session never clobbers the first) and checks it out BEFORE committing, so the tree lands there and the task branch tip never moves. Committing conflict markers is fine THERE and only there: PR #159's rule is that markers must not reach the branch `git add -A` and the mid-turn safety net PUSH, and a local rescue branch is neither - there is an explicit comment saying so, because the obvious 'fix' is to discard them and the tree is the only record of what the dead session was doing. Re-clone survives solely for the case where the rescue cannot be established at all. The abort rescue is surfaced as TIER TWO (mandatory) and rendered before both merges, since what it holds can change what the merges are supposed to produce; the Phase D detached rescue stays middle-tier but now names branch AND sha, because a rescue branch nobody is told about exists only on the volume and is barely better than the reflog entry it replaces. Platform noise (stale locks, half-clone, wrong-task wipe) is counted and logged only - `ccw_bootstrap_lock_cleared_total{lock}` and `ccw_bootstrap_workspace_recovered_total{kind}`, both label sets bounded by construction - since telling the agent burns prompt budget on something it cannot act on.
- 2026-08-10 (push-safety-net, semver:minor): mid-turn PUSH-ONLY safety net (`bootstrap.PushOnly` + `safetyPusher` in `cmd/wrapper/safetypush.go`, `BRANCH_PUSH_INTERVAL_SECONDS` default 120s, 0 disables). Agent pod `imp-mtg-mtg-decks-i37` committed at 07:45 and was OOMKilled at 07:51 inside a 42-minute turn; `/workspace` is the container writable layer with no volume, so the commit died with the pod. The wrapper already committed and pushed in `finalizeTurn`, so the gap was purely granularity, not capability. Push only - no `git add`, no `git commit` - is the load-bearing choice: no index mutation means no `.git/index.lock` contention with the agent's own concurrent git calls, no half-edited tree or conflict marker can be published, and the branch only advances by commits the agent chose to make. It writes no turn record: `rec.PushedRepos` means "this turn produced a commit" and the operator consumes it via `LastTurnPushedRepos`, so only `finalizeTurn` may set it. Two things the design had to work around: `PUSH_INTERVAL_SECONDS` was already taken by the METRICS pusher (`internal/pushclient`), hence the `BRANCH_` prefix; and `GitRunner` returns only an error with git's combined output deliberately dropped (it can carry credential-helper expansions), so `PushOnly`'s benign-outcome classification (up-to-date / non-fast-forward / fetch first) only fires for a runner that surfaces the text - in the pod every failure is simply warned and counted (`ccw_safety_push_total`), never fatal. Behaviour change for the agent, so the injected global CLAUDE.md gained an `autoPushDirective` block: commits are public the moment they are made, amend/squash/reword is out because force-push is denied, make a new commit instead. Review caught the interesting bug there: the block was first gated on `TaskBranch != ""` alone, but the real off switch is the interval, so `BRANCH_PUSH_INTERVAL_SECONDS=0` still promised the agent a push that never happened - the same lie the read-only-checkout gate exists to prevent, reached through the other input. Fixed by threading `BranchPushInterval` into `bootstrap.Params` and giving both consumers ONE exported predicate, `bootstrap.AutoPushEnabled(taskBranch, interval)`: `safetyPusher.Enabled` decides whether the ticker runs, `autoPushDirective` decides whether the agent is told it runs, and a duplicated condition is exactly how prose and behaviour drift apart silently.
- 2026-08-09 (stall-detection W4, semver:major): `POST /v1/interrupt` writes a single `\x1b` under `ptyMu` (`internal/session/interrupt.go`). ESC was spiked on CLI 2.1.201 and 2.1.226: it cancels synchronously in ~40ms and DURING a running tool call, unlike pasted text, which the CLI only consumes at the next tool-call boundary and which is therefore useless against a turn wedged inside one tool call. Session, sessionId, transcript JSONL, workspace and full context all survive; the next turn runs normally in the same session. THE CATCH, and the reason this phase needed a test more than it needed code: an ESC'd turn produces NO `end_turn`, no `stop_reason`, and NO Stop hook at all (checked the spike transcript - the next `stop_hook_summary` entry belongs to the FOLLOWING turn). Every completion path in the manager keys on one of those, so without new machinery `mgr.current` is never cleared and the session sits Busy for the rest of the pod's life - and since the operator's own escalation is what sends the ESC and the very next thing it does is `POST /v1/messages` for the handoff turn, the interrupt would have made the pod strictly less useful than leaving the turn alone. Detection is `transcript.WasInterrupted(path) bool`: the LAST conversation entry (system/summary/attachment/file-history-snapshot skipped - the CLI writes two of those between the marker and the next prompt) must be a `type:"user"` line whose `message.content` array holds a text block with prefix `[Request interrupted by user`. Both real variants confirmed against ~/.claude/projects: `[Request interrupted by user for tool use]` (47 occurrences, ESC mid-tool) and `[Request interrupted by user]` (28, ESC while streaming text); matched on the shared PREFIX from the first byte, so a model quoting the phrase cannot resolve its own turn. Deliberately not keyed on the sibling `interruptedMessageId` envelope field. Resolution polls the transcript every 200ms for up to 30s (`awaitInterruptedTurn`) rather than hooking the Tailer, because `CCW_LOG_TRANSCRIPT=false` means there is no Tailer and the turn must still resolve; past the deadline the turn is LEFT ALONE (`ccw_interrupts_total{result=unconfirmed}`) since resolving a turn that may still be running is worse than an unresolved one the operator can still see. New `turn.Store.Interrupt` writes State=Failed + StopReason=`interrupted` + FinalText from `LastAssistant`: Failed not Complete because the agent did not finish and a Complete would let the operator advance a Task on a turn it deliberately cut short, but the partial text is kept because it is often the only record of what was happening. Second half: `mgr.timer` no longer calls `failTimeout` (deleted, zero callers) but `markStallSuspected` - stamps `stallSuspectedSince` ONCE per stall (so the field measures how long the silence has lasted, not how long since the last re-arm), counts `ccw_turn_stall_suspected_total`, logs WARN, and RE-ARMS. Cleared by `onTailerActivity` and `clearCurrentLocked`; probe-originated activity does NOT clear it (same exclusion as W3, or the operator's escalation would erase its own evidence). **The wrapper now has NO time-based bound on a turn at all** - only `admit()`/PodTTL, which refuses to START work past the deadline. Seven existing tests asserted the opposite behaviour and were inverted rather than deleted (TestTurnTimeout_FailsAndFiresCallback -> _NoLongerFailsTheTurn, plus the probe/subagent/stale-turn timer-reset regressions, which now observe the stall stamp instead of a Failed record). **This image MUST NOT deploy before operator phase O2 is live: W4 removes the only killer a hung turn has, and the old operator's `stalledTurnStop` waits for a wrapper that will now never go idle.**
- 2026-08-09 (fix/outcome-reprompt-only-retryable, tatara-operator#578) **The outcome re-prompt fired on ANY `is_error` tool_result with a MANDATORY "call it again... Do not finish the turn until the call succeeds" directive, which turned one doomed 400 into a pod-recreation loop.** Live: Task `mt-i-mtg-decks-22-3f4594d8ce81d4d0` got `400 {"error":"this task owns no open MR"}` from `submit_outcome` (its PR had merged out of band; operator-side defect, fixed there), `FailedCriticalOutcome` saw the `is_error`, `reprompt` told it this was MANDATORY, and it re-submitted the IDENTICAL call three times per turn across 7 pod runs and 3 pod recreations before parking `no-outcome`. **A 4xx is a client error: the identical call can never succeed, so a mandatory retry directive against one is unsatisfiable by construction.** Fix: NEW `transcript.OutcomeErrorStatus` extracts an HTTP status from the tool_result text, anchored on real status positions (start of text, or after `http`/`status`/`status code`/`code`/`->`/`returned`) so a bare number in [400,599] - an issue number like `#578` - is NOT read as one; `retryableOutcomeFailure` is `5xx || no-status`. **An UNCLASSIFIABLE text is RETRYABLE**, deliberately: a transport failure is exactly when a retry is right and must never be downgraded to "your fault, do not retry". `repromptDirective` now has two forms - the mandatory one ONLY for retryable, and for a 4xx a corrective refusal that forbids an unchanged resend AND explicitly authorises the agent to STOP and `report_internal_issue` (its only legal exit from a precondition it cannot influence). The re-prompt is NOT removed for 4xx: a malformed payload is a 4xx the agent really can correct, which is why this path exists. **Classification is by STATUS CLASS, not a list of the operator's individual failure modes** - such a list drifts the moment either side adds one; a permanent 5xx costs at most `maxOutcomeReprompts` wasted turns, a 4xx read as retryable costs a burned Task. Metric label `reprompted_corrective` distinguishes the 4xx path from `reprompted`. **Review round 1 caught a real FALSE-POSITIVE hole and it is worth remembering:** the marker scan was an unanchored `strings.HasPrefix` at every index, so `code` and `returned` matched as SUFFIXES of ordinary words - `scanned barcode 404`, `failed to decode 500 bytes`, `unreturned 502` all parsed as statuses. That is this very fix running backwards (a bogus 4xx strips the mandatory directive off a genuinely retryable failure), so the marker now requires a non-word byte before it (`isWordByte`). `make test lint` green; semver:patch.
